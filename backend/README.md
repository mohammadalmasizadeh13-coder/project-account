# سرور حسابداری زرنگار

سرور FastAPI ثبت‌نام، نشست کاربران، دفتر خصوصی هر حساب، دسترسی همکاران و ذخیره‌سازی پایدار را مدیریت می‌کند. هر ثبت‌نام عمومی یک مالک و دفتر مستقل می‌سازد. همکاران به حساب مالک خود متصل‌اند و اطلاعات حساب دیگری را دریافت یا ویرایش نمی‌کنند.

## اجرای محلی

از پوشهٔ `backend`، با پایتون ۳٫۱۲ یا جدیدتر:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
Copy-Item .env.example .env
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000 --env-file .env
```

اگر `.env` از قبل وجود دارد آن را بازنویسی نکنید. نمونهٔ محیط برای HTTP محلی، `NOOR_COOKIE_SECURE=false` دارد. در HTTPS عمومی این مقدار را `true` کنید. `FRONTEND_ORIGINS` باید نشانی دقیق رابط، شامل طرح و درگاه، را داشته باشد. فایل محیط با گزینهٔ `--env-file` خوانده می‌شود.

نام و هش مالک محیط برای ثبت‌نام عادی لازم نیستند. `NOOR_OWNER_USERNAME` و `NOOR_OWNER_PASSWORD_HASH` فقط برای ایجاد مالک اولیهٔ نصب قدیمی بدون کاربر کاربرد دارند. در صورت نیاز، دستور زیر رمز را مخفی دریافت و هش تولید می‌کند:

```powershell
.\.venv\Scripts\python.exe -m app.create_owner
```

حساب‌های ذخیره‌شده، رمزهای تغییرکرده و دفتر موجود با راه‌اندازی مجدد یا تنظیمات اولیه بازنویسی نمی‌شوند. ارتقای پایگاه داده دفتر قبلی را به حساب موجود متصل می‌کند؛ حساب‌های ثبت‌نام‌شدهٔ بعدی با دفتر خالی شروع می‌کنند.

## ثبت‌نام و دسترسی

ثبت‌نام و ورود نام کاربری و رمز می‌خواهند. نام کاربری با یکسان‌سازی نویسه‌ها، «ی/ي»، «ک/ك» و فاصله‌ها یکتا می‌شود. رمز حساب تازه باید ۸ تا ۲۵۶ نویسه باشد. ساخت حساب و دفتر در یک تراکنش انجام می‌شود و پاسخ ثبت‌نام، نشست ورود را نیز ایجاد می‌کند.

نشست در کوکی `HttpOnly` و `SameSite=Lax` ذخیره می‌شود؛ در HTTPS باید `Secure` باشد. سرور هش شناسهٔ نشست را نگه می‌دارد و نشست پس از هشت ساعت منقضی می‌شود. نوشتن در دفتر علاوه بر نشست، مبدأ مجاز و هدر `X-CSRF-Token` می‌خواهد. ثبت‌نام و ورود نیز مبدأ مجاز می‌خواهند و درخواست‌های احراز هویت محدودسازی تلاش دارند.

مالک بخش‌های حساب خودش را مدیریت می‌کند. برای کاربر همکار، مجوزهای خواندن و نوشتن اسناد، مشتریان، همکاران تجاری، نرخ‌ها، خریدهای تراز طلا و چک‌ها جدا هستند. دادهٔ بخش‌های فاقد مجوز خواندن از پاسخ حذف می‌شود. ارسال یک بخش بدون مجوز نوشتن، کل ذخیره را رد می‌کند. تغییر مجوز، غیرفعال‌کردن یا بازنشانی رمز کاربر همکار، نشست‌های او را باطل می‌کند. مدیریت کاربران و پشتیبان فقط در محدودهٔ همان حساب انجام می‌شود.

## مسیرهای اصلی

نام `/api/owner` برای سازگاری قرارداد حسابداری حفظ شده است و همهٔ این مسیرها به حساب کاربر واردشده محدودند.

| مسیر | کاربرد |
| --- | --- |
| `GET /api/health` | بررسی آماده‌بودن سرویس |
| `POST /api/auth/register` | ساخت حساب با `{username,password,galleryName}` و ایجاد نشست |
| `POST /api/auth/login` | ورود با `{username,password}` |
| `GET /api/auth/session` | دریافت کاربر و توکن امنیتی نشست |
| `POST /api/auth/logout` | ابطال نشست |
| `POST /api/auth/password` | تغییر رمز با `{currentPassword,newPassword}` و ساخت نشست تازه |
| `PATCH /api/owner/profile` | ثبت یا اصلاح نام گالری با `{galleryName}` فقط توسط مالک حساب |
| `GET, POST /api/owner/users` | فهرست و ساخت همکار در حساب مالک |
| `PATCH /api/owner/users/{id}` | تغییر مجوز، فعال‌بودن یا رمز همکار همان حساب |
| `GET, PUT /api/owner/workspace` | خواندن و ذخیرهٔ دفتر با `{revision,data}` |
| `POST /api/owner/workspace/import` | انتقال دفتر قدیمی با `{data,sourceUsername}` |
| `POST /api/owner/inventory` | افزودن موجودی با `{revision,item,requestId}` |
| `PATCH /api/owner/inventory/{id}` | اصلاح موجودی با `{revision,changes}` |
| `DELETE /api/owner/inventory/{id}` | حذف مجاز موجودی با `{revision}` |
| `GET, POST /api/owner/partners` | فهرست و ایجاد طرف تجاری همان حساب |
| `PATCH /api/owner/partners/{id}` | ویرایش مشخصات طرف تجاری |
| `POST /api/owner/partners/{id}/invoices` | ثبت فاکتور خرید، موجودی و گردش بدهی در یک تراکنش |
| `PATCH /api/owner/partners/{id}/invoices/{entryId}` | ویرایش اتمیک سند همکار با حفظ نسخهٔ محاسبه، شمارهٔ سند و کنترل موجودی |
| `POST /api/owner/partners/{id}/settlements` | ثبت پرداخت، دریافت یا حواله در دفتر طرف تجاری |
| `PATCH /api/owner/partners/{id}/settlements/{entryId}` | ویرایش دریافت، پرداخت یا حوالهٔ مستقل با حفظ هویت سند و محاسبهٔ دوبارهٔ مانده‌ها |

پاسخ ورود و ثبت‌نام شامل `user` و `csrfToken` است؛ `user.accountId` حساب حسابداری نشست را مشخص می‌کند. هش رمز در پاسخ وجود ندارد.

نام گالری هنگام ثبت‌نام الزامی است و پس از یکسان‌سازی حروف فارسی و فاصله‌ها باید بین ۱ تا ۱۲۰ نویسه باشد. `user.galleryName` برای مالک و کاربران همکار از مشخصات همان حساب خوانده می‌شود. حساب‌های قدیمی تا زمان ثبت نام گالری، مقدار خالی دارند. سرور نام گالری را هنگام صدور سند و گردش همکار در `galleryName` ذخیره می‌کند؛ اصلاح سند یا تغییر نام گالری، نام ثبت‌شدهٔ اسناد قبلی را عوض نمی‌کند. انتقال پشتیبان هویت تاریخی اسناد را حفظ می‌کند و برای اسناد قدیمی فاقد نام، نمایش می‌تواند از نام فعلی حساب استفاده کند. مسیر اصلاح مشخصات نیز مانند دیگر تغییرات به مبدأ مجاز و توکن CSRF نیاز دارد.

دفتر شامل `documents`، `customers`، `partners`، `prices`، `openingSetup`، `goldPurchases` و `cheques` است. نسخهٔ `revision` با هر ذخیره به‌صورت اتمیک افزایش می‌یابد. ذخیره با نسخهٔ قدیمی پاسخ ۴۰۹ می‌دهد تا تغییرات جدید از بین نروند. افزودن موجودی با شناسهٔ ثابت `requestId` قابل تکرار است و تلاش مجدد همان درخواست موجودی تازه‌ای ایجاد نمی‌کند. اصلاح و حذف موجودی، ارتباط اسناد، فروش‌های متصل و ماندهٔ مشتری را نیز کنترل می‌کنند.

انتقال دفتر مرورگر فقط در دفتر خالی همان حساب انجام می‌شود. اگر سرور دفتر متفاوت و غیرخالی داشته باشد، انتقال با پاسخ ۴۰۹ رد می‌شود. این مسیر دو دفتر غیرخالی را خودکار ادغام نمی‌کند.

سند `misc-purchase` خرید طلای دست‌دوم یا کم‌عیار را در گروه `crafted` ثبت می‌کند. سرور با حفظ `weight` و `ayar` واقعی، `weight750 = weight * ayar / 750` را برای هر عدد و وزن معادل کل را در `itemWeight` محاسبه می‌کند. مبلغ از وزن معادل کل و `gramPrice` زمان ورود و هزینه‌های جانبی ثبت‌شده به دست می‌آید؛ سود و اجرت این نوع خرید صفر هستند. مقدار ارسالی معادل یا مبلغ نمی‌تواند محاسبهٔ سرور را تغییر دهد. اصلاح موجودی، مبلغ و سابقهٔ خرید مشتری را هماهنگ می‌کند و ماندهٔ صریح مشتری و تسویه‌های قبلی را حفظ می‌کند.

عملیات نوشتن طرف تجاری، `revision` و `requestId` می‌خواهند و مانند ذخیرهٔ دفتر، حساب، مجوز، مبدأ و توکن امنیتی را کنترل می‌کنند. گردش‌ها در `partners[].entries` با `goldDebit`، `goldCredit`، `tomanDebit` و `tomanCredit` ثبت می‌شوند و ماندهٔ جاری در `goldBalance` و `tomanBalance` نگهداری می‌شود. ماندهٔ مثبت یعنی بدهی ما به طرف تجاری. اجرت درصدی خرید به وزن معادل طلای ۷۵۰ اضافه می‌شود؛ پرداخت از بدهی کم می‌کند. دفتر مشتریان و طرف‌های تجاری مستقل‌اند. فاکتورهای ثبت‌شده و گردش‌های مالی از مسیر ذخیرهٔ کلی دفتر قابل تغییر یا حذف نیستند. حوالهٔ مستقل، موجودی صندوق را تغییر نمی‌دهد.

سند جدید همکار از رابط با `calculationVersion: 3` و `settlementUnit: "gold"` ثبت می‌شود. هر ردیف کالا `direction: "purchase" | "sale"` مستقل دارد؛ مقدار حذف‌شده از جهت اصلی سند گرفته می‌شود. خرید کار ساخته، فروش سکه و ارز یا آب‌شده و حواله می‌توانند در یک سند و یک گردش ثبت شوند. ردیف حواله `category: "remittance"`، `remittanceDirection: "debit" | "credit"` و `goldAmount` مثبت دارد و موجودی کالا ایجاد نمی‌کند. اسناد کالایی شماره و شناسهٔ تراکنش مشترک دارند؛ سندی که فقط حواله دارد نیز شماره می‌گیرد. جمع بدهکار و بستانکار جدا ذخیره می‌شوند و ماندهٔ خالص صفر نیز معتبر است. در فروش، مشخصات فیزیکی از `inventorySourceId` خوانده می‌شوند و کنترل مجموع فروش‌های یک کد، همهٔ ردیف‌ها را اتمیک رد یا ثبت می‌کند.

نرخ تبدیل `gold18Price` برای تمام ردیف‌های سند ثابت است. فی آب‌شده در `meltedFee` به تومان وارد می‌شود و نرخ هر گرم از `meltedFee / 4.3318` به دست می‌آید. مبلغ اصل آب‌شده برابر این نرخ ضرب در وزن معادل ۷۵۰ است؛ معادل بدهی طلا با تقسیم مبلغ بر `gold18Price` محاسبه می‌شود. اجرت درصدی بر مبلغ اصل، اجرت ثابت و هزینه به تعداد، و سود بر مجموع آنها محاسبه می‌شوند. پیش‌فرض سود کار ساخته ۷ درصد و سایر گروه‌ها صفر است؛ صفر صریح معتبر است. نرخ ارسالی `meltedGramPrice` نمی‌تواند محاسبهٔ فی را تغییر دهد. فی، نرخ مشتق‌شده و اجزای محاسبه در گردش و سند محفوظ می‌مانند. `paidGold` و معادل طلایی `paidToman` در همان گردش، برای جهت اصلی خرید بستانکار و برای فروش بدهکار هستند؛ بدهی تومانی جدید ایجاد نمی‌شود. قراردادهای نسخهٔ ۱ و ۲ و تکرار درخواست‌های قبلی با محاسبات تاریخی خود حفظ می‌شوند.

ویرایش سند همکار از مسیر اختصاصی، همان بدنهٔ ثبت با `requestId` تازه و `revision` فعلی را می‌گیرد. نسخه‌های محاسبهٔ ۱، ۲ و ۳ قابل ویرایش‌اند؛ نسخهٔ محاسبه و واحد تسویهٔ قبلی باید حفظ شوند. ردیف کالایی موجود باید `documentId` قبلی خود را بفرستد؛ ردیف تازه این فیلد را ندارد. شناسهٔ گردش، شمارهٔ سند و شناسهٔ ردیف‌های باقی‌مانده و پرداخت متصل حفظ و مانده‌ها دوباره محاسبه می‌شوند. حذف یا تغییر اقتصادی کالای دارای سابقهٔ فروش و فروش بیش از موجودی رد می‌شود. اسناد قدیمی با شناسه‌های ناقص، کالای اصلی مفقود یا چند تسویهٔ متصل، برای جلوگیری از تغییر نادرست دفتر رد می‌شوند. تغییرات پذیرفته‌شده همگی در یک تراکنش ذخیره می‌شوند و تکرار همان درخواست، سند یا گردش تکراری نمی‌سازد. مسیر عمومی ذخیرهٔ دفتر همچنان اجازهٔ بازنویسی گردش‌های همکار را ندارد.

دریافت‌وپرداخت مستقل از مسیر `settlements` با روش `gold`، `cash` یا `remittance` ثبت می‌شود؛ هر گردش `invoiceNumber` از شمارندهٔ مشترک اسناد و `transactionId` مستقل دارد و ردیف موجودی ایجاد نمی‌کند. مسیر ویرایش، بدنهٔ `PartnerSettlement` شامل تاریخ، جهت، مقادیر، روش پرداخت، مرجع و توضیحات را می‌گیرد و گردش اصلی را بدون تکرار جایگزین می‌کند؛ شناسه، زمان ایجاد و شمارهٔ سند حتی با تغییر روش پرداخت حفظ می‌شوند. گردش‌های قدیمی بدون شماره در اولین ویرایش شماره می‌گیرند. پرداخت دارای `linkedEntryId` باید همراه فاکتور اصلی ویرایش شود. ثبت و ویرایش گردش مستقل به مجوز `partners.write` نیاز دارد. خطای مقدار یا نوع گردش پاسخ ۴۲۲ و تعارض نسخه یا شناسهٔ درخواست پاسخ ۴۰۹ دارد؛ تلاش مجدد درخواست معتبر، شماره یا گردش تازه‌ای نمی‌سازد.

## نگهداری و آزمون

پایگاه دادهٔ محلی به‌صورت پیش‌فرض `zarnegaar.db` است. از پایگاه داده و پوشهٔ `uploads` در کنار هم پشتیبان بگیرید. در Compose، نام volume و مسیر پایگاه دادهٔ قبلی برای حفظ داده‌ها نگه داشته شده‌اند؛ حذف volume اطلاعات همهٔ حساب‌ها را از بین می‌برد.

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

آزمون‌ها ثبت‌نام، جداسازی حساب‌ها، مجوز همکاران، نشست، تغییر رمز، تعارض ذخیره و عملیات اسناد و موجودی را بررسی می‌کنند.
